1. Big picture

EasyFuel is a Node.js / Express API plus a React (Vite) SPA, packaged as one Docker container. On Contabo it sits behind Caddy (reverse proxy + automatic HTTPS) and talks to a shared PostgreSQL container over an internal Docker network named caddy.

┌──────────────────────────────────────────────────────────────────────────┐ │ PUBLIC INTERNET │ │ Browsers · Mobile apps · Ozow webhooks · Resend callbacks │ └────────────────────────────────┬───────────────────────────────────────┘ │ HTTPS :443 / HTTP :80 │ ▼ ┌──────────────────────────────────────────────────────────────────────────┐ │ CONTABO UBUNTU HOST (vmi3450363 · 169.58.40.94) │ │ │ │ ┌──────────────────────┐ Docker network: caddy │ │ │ caddy container │◄──────────────────────────────────────────┐ │ │ │ ports 80 + 443 │ │ │ │ │ Let's Encrypt SSL │ reverse_proxy easyfuel:5002 │ │ │ └──────────┬───────────┘ │ │ │ │ │ │ │ ▼ │ │ │ ┌──────────────────────┐ ┌─────────────────────────────┐ │ │ │ │ easyfuel container │────────►│ postgres container │───┘ │ │ │ Express + SPA │ SQL │ postgres:16 │ │ │ │ internal :5002 only │ │ DB: easyfuel │ │ │ │ volume: /app/storage│ │ also published │ │ │ └──────────────────────┘ │ 127.0.0.1:5432 (SSH only) │ │ │ └─────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────────────┘ ▲ │ SSH tunnel (you / DBeaver / pgAdmin) Developer laptop
Core idea Only Caddy is public. The app and database are private on the Docker network. You reach Postgres for admin tools through SSH, not through the open internet.

3. Containers & Docker network

Shared Docker network: caddy

All production pieces for this stack join the external network named caddy. Docker DNS then resolves short names:

  • caddy → reverse proxy container
  • easyfuel → app container
  • postgres → database container
Why the network is called caddy It already existed on the server. Postgres was already attached to it. EasyFuel and Docker Caddy join the same network so they can reach each other by name. Coolify networks exist on the host but are not used for EasyFuel.

Container roles

ContainerImage / locationPublished portsNotes
caddy caddy:2 · compose in /opt/caddy 80, 443 (public) Only public entry point
easyfuel ghcr.io/wasifali9/easy-fuel:latest · /opt/easyfuel None Reached only as easyfuel:5002 on Docker network
postgres postgres:16 127.0.0.1:5432 only Not on the public internet; SSH tunnel for GUIs

App compose shape

services:
  easyfuel:
    image: ghcr.io/wasifali9/easy-fuel:latest
    container_name: easyfuel
    env_file: .env
    volumes:
      - easyfuel_storage:/app/storage
    # NO ports: section
    networks:
      - caddy

networks:
  caddy:
    external: true

4. Request flow (HTTP / HTTPS / WebSocket)

Browser page load

1. User opens https://portal.easyfuel.ai 2. DNS → 169.58.40.94 3. Caddy terminates TLS (Let's Encrypt) 4. Caddyfile rule: portal.easyfuel.ai { reverse_proxy easyfuel:5002 } 5. Request reaches Express inside easyfuel 6. Express serves built SPA from dist/public (HTML/JS/CSS) and /api/* JSON routes

API call

Same origin: browser calls /api/... on https://portal.easyfuel.ai. Caddy forwards everything for that hostname to the app. Express routes handle auth, orders, payments, etc.

WebSocket

Realtime (chat, live updates) uses /ws on the same HTTP server. Caddy’s reverse_proxy upgrades WebSocket connections to the app container. Clients may authenticate with a session cookie (web) or a short-lived JWT / query token (mobile).

External webhooks (Ozow)

Ozow calls public HTTPS URLs under PUBLIC_APP_URL, e.g. https://portal.easyfuel.ai/api/webhooks/.... Those hit Caddy → easyfuel like any other HTTPS request. That is why DNS + SSL must be correct before live payments.

Trust proxy Express sets TRUST_PROXY=1 so Secure cookies and HTTPS-aware behavior work behind Caddy (X-Forwarded-Proto). Without this, logins can appear to succeed then lose the session cookie.

5. Application architecture (inside easyfuel)

One container runs one Node process. That process serves both the API and the compiled frontend.

Source layout (repo)

PathRole
server/Express API, auth, payments, storage, websockets, jobs
client/React SPA (Vite)
shared/Shared TypeScript + Drizzle schema
public/PWA assets copied into the build
mobile/Expo app (separate; not inside the Docker image)
migrations/ · schema/DB migration artifacts / SQL patches

Build output (what runs in production)

npm run build ├─ vite build → dist/public/ (SPA static files) └─ esbuild server → dist/index.js (+ split chunks) Docker runtime: node dist/index.js ├─ Express API /api/* ├─ Static SPA /* ├─ WebSocket /ws └─ Object files /objects/* (from /app/storage)

Why “single container for everything”

  • Matches how the app is already built: one process serves API + UI.
  • Simpler ops: one image, one healthcheck, one replica.
  • Does not mean Postgres or Caddy live inside the same container — those stay shared infra containers.

Main runtime modules

  • server/index.ts — boot, trust proxy, timers
  • server/routes.ts — HTTP route registration
  • server/auth.ts / auth-local.ts — sessions & JWT
  • server/db.ts — Postgres pool via DATABASE_URL
  • server/websocket.ts — realtime
  • server/ozow-*.ts — payments
  • server/local-object-storage.ts — disk uploads
  • server/static.ts — serve dist/public in production

6. Database architecture & access patterns

Two different connection styles (by design)

WhoHostHowExample
App (code) postgres Docker DNS on network caddy postgresql://easyfuel_app:***@postgres:5432/easyfuel
You (DBeaver / pgAdmin) localhost SSH tunnel into Contabo → host-bound 127.0.0.1:5432 SSH enabled in GUI; Main host = localhost, port 5432
Common mistake Putting localhost in the app DATABASE_URL inside Docker points at the container itself, not the Postgres container. Always use host postgres for the app.

Databases on this server

  • Cluster admin user: creativecloud (default DB was maindb)
  • EasyFuel app DB: easyfuel
  • EasyFuel app role: easyfuel_app

App data access

Runtime uses pg Pool + Drizzle. Sessions for the web app can use connect-pg-simple (Postgres session store). Refresh tokens for mobile JWT auth are stored hashed in local_auth_refresh_tokens.

7. Authentication architecture

EasyFuel uses local auth (not Supabase) in this Contabo setup.

Web (browser)

  • Primary: express-session cookie (e.g. session id in a Secure cookie)
  • Works because Caddy terminates HTTPS and Express trusts the proxy
  • Client often uses a placeholder access_token: "cookie-session" — that is not a real JWT

Mobile / Bearer API

  • Access JWT — short-lived, signed with JWT_ACCESS_SECRET
  • Refresh JWT — longer-lived, signed with JWT_REFRESH_SECRET, tracked in DB
  • Sent as Authorization: Bearer …

Other JWT uses of JWT_ACCESS_SECRET

  • Short-lived WebSocket tokens
  • Object view tokens — temporary links to open /objects/... files without a Bearer header
Why JWT secrets matter on Contabo If you omit them, the code falls back to weak development defaults. Changing secrets later invalidates existing mobile tokens (users must log in again).

8. File storage architecture

Default provider is local disk (OBJECT_STORAGE_PROVIDER=local). Files live under LOCAL_STORAGE_DIR (in Docker: /app/storage), backed by a Docker named volume so they survive container recreates.

Upload (authenticated) PUT /api/storage/upload/... │ ▼ /app/storage/private/<uuid>... ← Docker volume easyfuel_storage Download / view GET /objects/... │ session, Bearer, or object-view JWT ▼ stream file from volume

Optional S3/MinIO helpers exist in code but are not the Contabo default. Migrating from GoDaddy requires copying both the Postgres dump and the old storage/ folder.

9. Background jobs

Jobs run inside the same Node process using setInterval (not Redis/Bull, not a separate worker container):

  • Expiring KYC / documents — about every 6 hours
  • Unpaid delivery payment reminders — about every 12 hours
Scaling rule Keep one easyfuel replica. Multiple replicas would duplicate these timers.

10. CI/CD & deploy architecture

Developer pushes to main │ ▼ GitHub Actions (.github/workflows/deploy.yml) │ ├─ docker build (Node 20 multi-stage) │ VITE_MAPBOX_TOKEN baked into SPA ├─ docker push → ghcr.io/wasifali9/easy-fuel:latest ├─ scp docker-compose.yml → /opt/easyfuel/ └─ SSH → Contabo docker login ghcr.io docker pull docker compose up -d --force-recreate Result: new container image live in ~1–2 minutes

The Contabo host keeps secrets only in /opt/easyfuel/.env. The image itself should not contain production secrets.

Image build stages

  1. Build stage: npm ci → npm run build (Vite + esbuild)
  2. Runtime stage: production node_modules + dist/ → node dist/index.js

Vite is loaded only in development via dynamic import, so the production image does not need Vite as a runtime dependency.

13. Design rules (do / don’t)

DoDon’t
Publish 80/443 only on Caddy Publish app port 5002 to the internet
Use DB host postgres in app env Use localhost for the app inside Docker
Join network caddy Use Coolify for this app (it’s stopped / out of scope)
Keep secrets in server .env Commit .env to git or bake secrets into the image
Run one easyfuel replica Scale to many replicas while jobs are in-process timers
Persist /app/storage volume Assume uploads survive without a volume
